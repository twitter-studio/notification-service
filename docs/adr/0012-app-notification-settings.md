# ADR-0012: アプリの通知設定・削除・テスト通知

- 状態: 採用
- 日付: 2026-11-04
- 関連: notification-service#24、tweetbot#366、ADR-0006〜0011

## 背景

IOS-001 の通知設定には、再起動後の設定取得、通知アカウントの削除、通知が届くことを利用者自身で確かめる操作が必要になる。端末登録と中継資格情報の入口だけでは完結しない。端末のトークンと中継の秘密をアプリから取り出してテストを代行する方法は採らない。

## 決定

どの入口もアカウントのセッションを求める。対象のアカウントとインストールはセッションから決め、本文で送り先を受けない。

| 入口                        | 成功 | 内容                                                                                                           |
| --------------------------- | ---- | -------------------------------------------------------------------------------------------------------------- |
| GET /v1/settings            | 200  | 自分のインストールの端末 (ID・有効状態・確認済みか)、現在の中継資格情報の ID と期限を返す。存在しなければ null |
| DELETE /v1/account          | 204  | 自分の通知アカウントの秘密と端末情報を削除する。専用の新しい署名が必要                                         |
| POST /v1/notifications/test | 200  | 自分の有効・確認済み端末へ固定の一般的な通知を送る。応答の sent / queued は画面への到達を保証しない            |

### 設定

APNs トークン、暗号文、指紋、資格情報の秘密やハッシュ、セッショントークンは選択も返却もしない。中継資格情報の取り消し・期限切れは null で返す。応答はほかの /v1 と同じく no-store とする。

### 削除

`purpose: delete_account` の5分間・1回限りのチャレンジを使う。端末の P-256 鍵で、次を改行で結んだ文に署名する。改行は最後に付けない。

1. `twitter-studio/delete-account/v1`
2. チャレンジ
3. セッションのインストールの ID

別用途のチャレンジ、別の鍵の署名、別のインストールの署名は拒む。署名を確かめた後、インストールごとの `account-delete:` で5回/分の制限をかける。

チャレンジの消費、インストールがまだ自分の有効なものかの再確認、削除は1つの D1 バッチにする。先にアカウントを deleted にしてから子を消し、取り消し済みのインストールでは削除しない。既に deleted のアカウントの子が残っていれば掃除してよい。端末・所有確認・中継資格情報・セッション・受け付けの記録・日次枠・インストールを消す。アカウントの deleted の行と削除時刻、期限付きの使用済みチャレンジを残す。アカウント ID を条件に入れ、ほかのアカウントを変更しない。

応答後はセッションも中継資格情報も無効。再送 Queue は有効なインストールや端末を見つけられず送信しない。既に APNs に渡した通知は取り消せない。アプリは削除成功後に Keychain のアカウント情報を消す。端末の署名鍵を作り直す必要はなく、明示した新しい招待登録で別の通知アカウントを作れる。X のアカウントや認証には触れない。

### テスト通知

インストールごとの `test-notification:` で5回/分を数える。端末がない・未確認・停止・APNs による無効化済みなら409で送らない。端末が送信可能なときだけ、中継と共通の UTC 日次枠 (1,000件/アカウント) を1件使う。これによりテスト通知で中継の費用上限を迂回できない。専用の Worker や追加の資格情報は作らない。

固定の `loc-key: You have a new notification.`、sound: default、event_type: test を使う。本文、URL、ツイートの ID は受けない。通常の中継のイベント許可リストには test を足さない。送信は既存の APNs アダプターを通し、無効トークンの応答も通常と同じ照合条件で端末へ反映する。送れなければ503と Retry-After: 60を返す。APNs に送信済みでも、応答を失って再実行すると重複しうる。

再送には権限の根拠を区別して保存する。中継なら受理した資格情報の ID、テスト通知ならセッションのインストールの ID。前者は資格情報の取り消し・期限切れ、後者はインストールの取り消し・アカウント削除で止まる。どちらも端末の所有・確認・有効状態と登録の指紋・環境・topic を再確認する。中継資格情報を取り消しただけで、アプリ自身のテスト通知を使えなくしない。

## 検証

workerd で認証、秘密を含まない設定、署名・用途・チャレンジの使い回し、削除後の認証拒否と他アカウントの維持、未確認・停止・無効端末への送信拒否、回数制限と共通の日次枠、再送の取り消しを確かめる。OpenAPI を生成し直してから iOS のクライアントを生成する。実機の通知表示とタップ、削除の確認はテストとは別に記録する。

## 初期 sandbox の配置条件

今回の Queue 形式の変更では、旧形式を読み替える処理を加えない。まだリリースしておらず、保存形式を変えたときに前のデータの読み替えを作らない規則に従う。旧アダプターで行ったのは Queue を使わない所有確認だけで、利用者の Worker はまだ接続していない。

2026-11-04、配置前の Queue metrics は backlog_count: 0、backlog_bytes: 0、oldest_message_timestamp_ms: 0だった。この metrics は best-effort のため、実際に中継をまだ始めていないことも合わせて確認する。配置の直前にも空であることを確認し、待機中のメッセージがあれば配置を止める。利用者の接続後に形式を変える場合は、待機中の通知の扱いを先に決める。
