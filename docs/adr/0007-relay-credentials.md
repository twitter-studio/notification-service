# ADR-0007: 中継の資格情報の入れ替えと取り消し

Status: Accepted / 2026-11-04

## 背景

設計書 v1.1 の §3 と §4 は、利用者の Worker が使う中継の資格情報 (relay secret) を、1 回だけ見せ、利用者が入れ替えと取り消しをできるようにすることを求めている。入れ替えには、アカウントのセッションに加えて、新しい証明 (fresh proof) が要る。最初の資格情報は、登録のときに作る (ADR-0006)。

## 決定

- **形と置き方**: ADR-0006 のとおり。`tsr_` と 32 バイトの乱数。DB には SHA-256 だけを置き、平文は作った応答でだけ返す。
  - DB の関数は、ハッシュをブランドの型 (`BearerTokenHash`。作れるのは `hashBearerToken` だけ) で受ける。表には、43 文字の Base64URL (SHA-256 の Base64URL の形) の CHECK を付け、平文のトークン (47 文字) を置かせない。セッションのハッシュも同じ。トークンから頭の印を除いた乱数そのもの (43 文字) は、形では区別できないので、守りの本体はブランドの型。
- **確かめ** (`requireRelayCredential`): `Authorization: Bearer tsr_…` のハッシュで、取り消しておらず、期限内で、アカウントが有効な資格情報を引く。送り先のアカウントは、これだけで決める (ADR-0001)。
  - ハッシュは DB の索引で引く。引く時間からハッシュの一部が分かっても、256 ビットの乱数の元の値は探せないので、時間をそろえる比べ方はしない。
  - 使った時刻 (`last_used_at`) を、1 時間に 1 回まで書く。応答を待たせず (`waitUntil`)、書けなくても中継は通す。今は API で読めない。使っていない資格情報を知らせる仕組みや一覧の入口を足すときに使う。
  - 中継の入口の回数の制限は、ADR-0009 (アカウントごと)。利用者の Worker からの要求は Cloudflare の IP から届き、多くの利用者で同じ IP になりうるので、IP ごとの制限 (`CLIENT_RATE_LIMITER`) はそのまま使えないと考えている (文書でも、デプロイした Worker でもまだ確かめていない。API-003 で確かめる)。
  - アカウントに、取り消していないインストールがあることも見る。インストールを取り消すと (`revokeInstallation`)、そのアカウントの資格情報も同じバッチで取り消す。v1 のアカウントはインストールを 1 つだけ持ち、取り消した後は、持ち主が資格情報を取り消すためのセッションを作れないため。中継は 401 になり、利用者の Worker から利用者に伝わる。
- **入れ替え** (`POST /v1/relay-credentials/rotate`): アカウントのセッションと、端末の鍵の署名で行う (201)。
  - 署名する文は `twitter-studio/relay-credential/v1\n<チャレンジ>\n<インストールの ID>`。チャレンジは用途 `relay_credential` で出したもの。インストールはセッションのもの。
  - 1 つのバッチで、チャレンジを使ったものとして記録し、アカウントの使える資格情報をすべて取り消し、新しいものを置く。続けて、または同時に入れ替えても、使えるのは最後のものだけ。
  - 取り消しと置き直しは、同じ条件で絞る。署名を確かめてからバッチまでのあいだにインストールやアカウントが止まったとき、1 時間に作れる数を超えたときは、何も変えず、前の資格情報を残す。
  - 1 つのアカウントが 1 時間に作れる資格情報は 10 まで (登録で作ったものを含む)。行が残るので、DB で正確に数える。超えたら 429 (`Retry-After: 3600`)。
  - 応答で、新しい資格情報の ID と秘密を返す。秘密を返すのは、この応答だけ。
  - インストールごとに、署名を確かめた後に数えて、1 分に 5 回まで (`INSTALLATION_RATE_LIMITER`、`relay-credential-rotate:<インストールの ID>`)。セッションの作り直しや、取り消しとは別に数え、漏れたセッションで入れ替えの枠を使わせない。
  - アプリは、入れ替えを 1 つずつ送る (2 つ送ると、先に返った秘密がもう取り消されていることがある)。応答を受け取れなかったときは、前の資格情報は取り消されているので、新しいチャレンジで入れ替え直す (同じチャレンジでは 409)。送り直すときは、いつも新しいチャレンジを取る (1 時間の上限の 429 ではチャレンジを使ったことになり、1 分の制限の 429 ではならない)。
- **取り消し** (`DELETE /v1/relay-credentials/{id}`): アカウントのセッションで行う (204)。
  - ほかのアカウントのもの、取り消し済み、ないものは、区別せずに 404。
  - 取り消すと、使える資格情報がなくなり、中継は 401 になる。使い直すには、入れ替えで新しいものを作る。
  - インストールごとに 1 分に 5 回まで (`relay-credential-revoke:<インストールの ID>`)。入れ替えとは別に数えるので、ここを使い切られても、持ち主は入れ替えで前のものを取り消せる。
- **掃除**: 取り消してから 7 日を過ぎた資格情報の行は、定期の掃除で消す (1 時間に作れる数を数えるのに使うので、それより長く残す)。
- **鍵をなくしたとき** (ADR-0006): 新しいアカウントとして登録し直し、前のインストールは取り消さない。前のアカウントの資格情報は、持ち主が取り消せないまま使える状態で残る。使われなくなったアカウントとして消す仕組み (notification-service#14) で閉じる。
- **期限**: 既定では付けない。資格情報は利用者の Worker に置かれ、期限で切れると、利用者が気づかないまま通知が止まるため。表には期限の列があり、確かめでは期限を見る。期限を付けるときは、切れる前に知らせる仕組みと一緒に決める。
- 利用者の Worker は、中継の 401 をやり直さない。資格情報を入れ替えたら、利用者が Worker の秘密 (`RELAY_TOKEN`) を新しい値にする (USER-001)。

## 採らなかった案

- **セッションだけで入れ替える**: 漏れたセッション (1 時間) で、新しい秘密を作れてしまう。取り消しは能力を失うだけなので、セッションだけでよい。
- **入れ替えた後も、前の資格情報を少しのあいだ使えるようにする**: 漏れた資格情報を入れ替えて止めたいときに、すぐ止まらない。設計書も、入れ替えで前のものを取り消すとしている。
- **サーバーの鍵の HMAC (pepper) で置く**: 32 バイトの乱数は、ハッシュから総当たりで探せないので、鍵の管理を増やす意味がない (ADR-0006)。
- **資格情報の一覧を返す入口**: v1 のアカウントは使える資格情報を 1 つだけ持ち、ID は登録と入れ替えの応答で返す。要るようになったら足す。

## 影響

- アプリ (IOS-001) は、設定に入れ替えと取り消しを置き、入れ替えたときは秘密を 1 回だけ見せる。
- 利用者の Worker (USER-001) は、401 をやり直さず、利用者に知らせる。
- 中継の入口 (API-003) は、`requireRelayCredential` を付け、アカウントごとの回数の制限を足す。偽のトークンで D1 を引かせる要求の数え方は、デプロイした Worker で IP を確かめてから決める (ADR-0009)。
- 本番の前に (QA-001)、Workers Logs で `Authorization` ヘッダーの値が伏せられるかを確かめる。Workers の Tail の文書は、名前に "auth" を含むヘッダーを既定で伏せるとしているが、伏せ方は経験則で誤ることがあるとも書いている。
