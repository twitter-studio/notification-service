# ADR-0005: APNs のデバイストークンの暗号化と指紋

Status: Accepted / 2026-11-04

## 背景

設計書 v1.1 の §3 は、APNs のデバイストークンを、Cloudflare の秘密で管理する鍵で暗号化して置き、版のある鍵 ID で入れ替えることを求めている。DB でトークンを一意にする (ADR-0004) には、平文を置かずに比べられる値も要る。DB-001 のセキュリティのレビュー (notification-service#13) で、鍵の入れ替えの手順、指紋の鍵の取り違え、暗号文と DB の行の結び付きに問題があると分かり、この形にした。

## 決定

- **暗号化**: AES-256-GCM (Web Crypto)。
  - IV は毎回 12 バイトの乱数にする。
  - 追加の認証データに、用途、版、鍵の ID、端末の行 (インストール、環境、topic) を入れる。DB の暗号文をほかの行に写しても読めない (行はインストールに 1 つで、トークンが変わっても同じ行を書き換える)。
  - 暗号文の形は `v1.<鍵の ID>.<IV>.<暗号文>` (Base64URL)。読むときは、形 (IV が 12 バイト、余計な文字がないこと)、読んだトークンの形、行の指紋と合うことを確かめる。
- **指紋**: HMAC-SHA256 (秘密 `DEVICE_TOKEN_FINGERPRINT_KEY`)。形は `f1.<HMAC>` で、版を付ける。暗号化の鍵と同じ値は拒む。
- **鍵束と、鍵の確かめの値**
  - 暗号化の鍵は、秘密 `DEVICE_TOKEN_KEYS` に JSON で置く (`{"current":"<鍵の ID>","keys":{"<鍵の ID>":"<32 バイトの Base64>"}}`)。新しい暗号文は current の鍵で作る。current 以外の鍵は、読むだけに使う。
  - 鍵ごとの確かめの値 (KCV) を、秘密でない設定 `DEVICE_TOKEN_KEY_CHECKS` (`wrangler.jsonc` の vars) に置く。値は、SHA-256(`twitter-studio/key-check/v1` ‖ 鍵) の先頭 8 バイト。鍵を読むときに比べ、合わなければ失敗する。秘密は後から読めないので、入れ替えのたびに古い鍵も打ち直す。そのときの打ち間違いで、古い暗号文が黙って読めなくなるのを防ぐ。値は `apps/api/scripts/key-check.mjs` で作る。
- **トークンの形**: 16 進数で 16〜128 バイトのものだけを受け付け、小文字にそろえてから暗号化し、指紋を作る (Apple はトークンの長さを決めていない)。
- **DB に平文を置かない**
  - 暗号文と指紋は、ブランドの型 (`DeviceTokenCiphertext`、`DeviceTokenFingerprint`) で受け、`sealDeviceToken` でしか作らない。
  - DB にも、形 (`v[0-9]*.*`、`f[0-9]*.*`) の CHECK を付ける。
- **ログ**: トークン、鍵、暗号文、指紋は、ログにもエラーの文にも、テレメトリにも出さない (設計書 §3、§9)。エラーは、種類 (`name`) だけで見分ける。
  - 端末から来たトークンの誤りは `InvalidDeviceTokenError` (422)。
  - 鍵の設定の誤りは `DeviceTokenKeyError` (500)。
  - DB の暗号文を読めないときは `DeviceTokenCiphertextError` (500)。
- **受け付けの記録の掃除**
  - 7 日残す。Cron (UTC の 18:17、日本時間の 3:17) で 1 日 1 回、それより古いものを 1,000 件ずつ区切って消す (1 回の掃除で 45 回まで。1 回の呼び出しで D1 に投げる問い合わせの上限の内側。ADR-0009)。上限まで消したときは、ログに `capped: true` を出す。続くなら、有料のプランにして区切りの回数を増やす。
  - 受け付けの時刻は、サーバーの時刻に限る。
  - 7 日より古いイベントのやり直し (リプレイ) は、受け付けるときに、イベントの時刻の新しさで拒む (ADR-0009)。拒む境目は、残す期間から、時計のずれと Cron の間隔を引いたもの。未来の時刻も拒む。送り手 (USER-001) のやり直しは、その期間の内側で終える。

## 採らなかった案

- **鍵の ID を列に置く**: 暗号文と列がずれうる。暗号文に入れれば、1 つの値で読める。
- **追加の認証データを、用途の文字列だけにする**: D1 に書けるが Worker の秘密は持たない人 (D1 を編集できる API トークンが漏れた場合など) が、暗号文をほかの行に写すと、ほかの端末へ送らせられる。
- **指紋を、鍵のない SHA-256 にする**: 漏れた指紋と、知られたトークンを突き合わせられる。
- **暗号化と指紋に同じ鍵を使う**: 片方を入れ替えると、もう片方も変わる。
- **鍵の確かめの値を置かない**: 打ち間違えた鍵でも、正しい形の 32 バイトなら取り込みが通り、古い暗号文が読めなくなっても気づけない。

## 影響

- **暗号化の鍵の入れ替え (2 段)**
  1. 新しい鍵の確かめの値を `DEVICE_TOKEN_KEY_CHECKS` (vars) に足して出し、全体に行き渡るのを待つ。確かめの値だけがあって秘密にない鍵は、読むときに無視される。
  2. 新しい鍵を `DEVICE_TOKEN_KEYS` の `keys` に足して (`wrangler secret put`)、current は古い鍵のまま出す。`wrangler secret put` はすぐ全体に出すので、確かめの値より先に秘密を置くと、鍵を読むたびに失敗し、すべての登録と送信が止まる。
  3. すべての版に新しい鍵が行き渡ってから、current を新しい鍵にする。段階的なデプロイでは、古い版と新しい版が同時に要求を受けるので、current まで一度に変えると、新しい鍵の暗号文を古い版が読めない。
  - 新しい鍵を持たない版 (手順 2 より前) へは戻さない。戻すと、新しい鍵で作った暗号文を読めなくなる。
  - 古い鍵は、その鍵の暗号文がなくなるまで残す。数えるには `SELECT count(*) FROM devices WHERE apns_token_ciphertext LIKE 'v1.<鍵の ID>.%'`。暗号文を作り直す処理は、要るときに足す。
  - 1 つの鍵で暗号化してよいのは、およそ 2^32 回まで (乱数の IV の AES-GCM)。秘密は 1 つ 5 KB までなので、古い鍵は数十個までに保つ。
  - 鍵の値は、ファイルに書かず、パスワード管理のツールなどから `scripts/key-check.mjs` と `wrangler secret put` に渡す。
- **指紋の鍵の入れ替え**: DB の一意の索引と、端末の突き合わせに使っているので、入れ替えるなら、全部の端末の暗号文を読んで指紋を作り直す処理が要る。今は入れ替えない前提にする。取り違えは、鍵の確かめの値で起動時に (鍵を読むときに) 見つける。
- 秘密の値は、手元では `.dev.vars` (コミットしない) に置き、名前だけを `.dev.vars.example` に書く。テストでは、テストだけの鍵と確かめの値を `vitest.config.ts` で渡す。
- 使わなくなった端末 (APNs が無効と返したもの、止めたもの) の暗号文を消す方針は、別の Issue で決める。
