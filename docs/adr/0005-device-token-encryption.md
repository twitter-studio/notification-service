# ADR-0005: APNs のデバイストークンの暗号化と指紋

Status: Accepted / 2026-11-04

## 背景

設計書 v1.1 の §3 は、APNs のデバイストークンを、Cloudflare の秘密で管理する鍵で暗号化して置き、版のある鍵 ID で入れ替えることを求めている。DB でトークンを一意にする (ADR-0004) には、平文を置かずに比べられる値も要る。

## 決定

- **暗号化**: AES-256-GCM (Web Crypto)。
  - IV は毎回 12 バイトの乱数にする。
  - 用途の文字列 (`twitter-studio/apns-device-token/v1`) を追加の認証データにして、ほかの用途の暗号文を読ませない。
  - 暗号文の形は `v1.<鍵の ID>.<IV>.<暗号文>` (Base64URL)。鍵の ID を暗号文に入れるので、DB に列は足さない。
- **鍵束**: 秘密 `DEVICE_TOKEN_KEYS` に JSON で置く (`{"current":"<鍵の ID>","keys":{"<鍵の ID>":"<32 バイトの Base64>"}}`)。
  - 新しい暗号文は current の鍵で作る。読むときは、暗号文に書かれた鍵の ID の鍵を使う。
- **指紋**: HMAC-SHA256 (秘密 `DEVICE_TOKEN_FINGERPRINT_KEY`)。
  - DB でトークンを一意にするのと、APNs の応答と端末を突き合わせるのに使う。
  - 鍵がなければ、指紋からトークンを総当たりで探せない。
- **トークンの形**: 16 進数で 16〜128 バイトのものだけを受け付け、小文字にそろえてから暗号化し、指紋を作る (Apple はトークンの長さを決めていない)。
- **受け付けの記録**: 7 日残す。Cron で 1 日 1 回、それより古いものを消す (送り手がやり直す期間 1 日より長くする)。

## 採らなかった案

- **鍵の ID を列に置く**: 暗号文と列がずれうる。暗号文に入れれば、1 つの値で読める。
- **指紋を、鍵のない SHA-256 にする**: トークンは 32 バイトの乱数に近いが、漏れた指紋と、知られたトークンを突き合わせられる。HMAC なら、鍵がない人は突き合わせられない。
- **暗号化と指紋に同じ鍵を使う**: 用途の違う鍵を分けておけば、片方を入れ替えても、もう片方に影響しない。

## 影響

- **暗号化の鍵の入れ替え**: 新しい鍵を `keys` に足して `current` にし、`wrangler secret put DEVICE_TOKEN_KEYS` で置き直す。古い鍵は、古い暗号文がなくなるまで残す (暗号文を作り直す処理は、要るときに足す)。
- **指紋の鍵の入れ替え**: DB の一意の索引に使っているので、入れ替えるなら、全部の端末の指紋を作り直す処理が要る。今は入れ替えない前提にする。
- 秘密の値は、手元では `.dev.vars` (コミットしない) に置き、名前だけを `.dev.vars.example` に書く。テストでは、テストだけの鍵を `vitest.config.ts` で渡す。
