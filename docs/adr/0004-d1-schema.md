# ADR-0004: D1 のスキーマで、設計書 §3 から変えたこと

Status: Accepted / 2026-11-04

## 背景

設計書 v1.1 の §3 に D1 のスキーマの案がある。DB-001 のレビュー (notification-service#12) で、案のままでは次の問題があると分かった。
- 時刻を `CURRENT_TIMESTAMP` の文字列で持つと、アプリの時刻 (ISO 8601) と文字列で比べたときに、期限の判定がずれる。
- 端末の登録が、トークンが同じというだけで、ほかのアカウントの端末を自分のものにできる。
- 利用者が止めた端末が、登録のやり直しで有効に戻る。
- 登録のやり直しで、アカウントが 2 つできる。

## 決定

- **時刻**: UNIX 時間のミリ秒の整数で持つ (Drizzle の `timestamp_ms`)。形の違いで比べ方がずれることがない。
- **外部キー**: すべて `ON DELETE CASCADE`。アカウントの行を消すと、インストール、端末、資格情報、受け付けの記録も消える。`delivery_dedup.account_id` にも外部キーを付けた。
- **インストール**:
  - `public_key` を一意にする。同じ公開鍵での登録のやり直しは、既存のものを返す。
  - 有効なインストールは、アカウントに 1 つ (部分的な一意の索引)。
- **登録**: アカウント、インストール、中継の資格情報を、1 つのバッチで作る (設計書 §3 の手順 3)。
- **端末**:
  - インストールごとに 1 つ (`installation_id` を一意にする)。トークンが変わったら、同じ行を書き換える。
  - 状態は `active`、`disabled_by_user`、`invalidated` で持つ。登録し直したとき、`disabled_by_user` は止めたまま、`invalidated` は有効に戻す。
  - 登録の文は、インストールの持ち主と状態を確かめ、それを書き込みと同じ 1 つの文で行う。
  - ほかのインストールが同じトークンを持っていたら、移さずに conflict にする。移すときは、トークンを持っていることを別に確かめる (APNS-002 などで決める)。
  - APNs の無効の応答で止めるのは、送ったときのトークンの指紋と合うときだけ (間に入れ替わった新しいトークンを止めない)。
- **受け付けの記録**: 受け付けたあとに送れなかったら、記録を消して (`releaseEvent`)、送り手のやり直しを受け付ける。記録を残す期間は、送り手がやり直す期間より長くする。

## 採らなかった案

- 時刻を ISO 8601 の文字列にそろえる: 生の SQL で `CURRENT_TIMESTAMP` と比べると、またずれる。DB で形を強制するには、長い CHECK が要る。
- 同じトークンを、最後に登録したインストールへ移す: トークンだけでは持ち主の証明にならない (設計書 §2、§3.8)。トークンを知っている人が、ほかの人の端末を乗っ取れる。
- 端末を `enabled` の 1 つの値で持つ: 利用者が止めたのか、APNs が無効と返したのかを区別できない。

## 影響

- D1 で親の表を作り直す migration は、drizzle-kit が出す `PRAGMA foreign_keys=OFF` が効かない (D1 はトランザクションの中で外部キーを確かめ続ける)。その場合だけ、作った SQL を `PRAGMA defer_foreign_keys = on` に直す (AGENTS.md)。
- CI で `drizzle-kit generate` を動かし、`schema.ts` と migration がずれていないことを確かめる。
