# ADR-0004: D1 のスキーマで、設計書 §3 から変えたこと

Status: Accepted / 2026-11-04

## 背景

設計書 v1.1 の §3 に D1 のスキーマの案がある。DB-001 の 2 回のレビュー (notification-service#12) で、案のままや最初の直し方では、次の問題があると分かった。
- 時刻を `CURRENT_TIMESTAMP` の文字列で持つと、アプリの時刻 (ISO 8601) と文字列で比べたときに、期限の判定がずれる。
- 端末の登録が、トークンが同じというだけで、ほかのアカウントの端末を自分のものにできる。まだ登録されていないトークンは、知っている人が先に登録できる。
- 利用者が止めた端末が、登録のやり直しで有効に戻る。
- 登録のやり直しで、アカウントが 2 つできる。
- 外部キーを `ON DELETE CASCADE` にすると、D1 で親の表を作り直す migration (`DROP TABLE`) が、子の行をすべて消す。

## 決定

- **時刻**: UNIX 時間のミリ秒の整数で持つ (Drizzle の `timestamp_ms`)。時刻はアプリから渡す。既定の値は秒までにし、`unixepoch('subsec')` (SQLite 3.42 以降) に頼らない。
- **外部キー**: `ON DELETE` は NO ACTION のまま (CASCADE にしない)。アカウントを消すときは、子の行から順に 1 つのバッチで消し、アカウントの行は `deleted` として残す (`deleteAccount`)。
- **インストール**:
  - `public_key` を一意にする。同じ公開鍵での登録のやり直しは、有効なアカウントなら既存のものを返す。
  - 有効なインストールは、アカウントに 1 つ (部分的な一意の索引)。
  - 取り消すときは、端末の行も消して、トークンを手放す (`revokeInstallation`)。
  - `attestation_state` は pending、verified、not_supported に限る (意味は AUTH-001 で決める)。
- **登録**: アカウント、インストール、中継の資格情報を、1 つのバッチで作る (設計書 §3 の手順 3)。
- **端末**:
  - インストールごとに 1 つ。トークンが変わったら、同じ行を書き換える。
  - 状態は `active`、`disabled_by_user`、`invalidated` で持つ。登録し直したとき、`disabled_by_user` は止めたまま、`invalidated` は有効に戻す。
  - トークンを持っていることを確かめた時刻 (`verified_at`) を持ち、確かめた端末にだけ送る。トークンが変わったら空に戻す。確かめ方は ADR-0008 (確かめの code を push で送り、アプリが返す)。
  - 登録の文は、インストールの持ち主と状態の確かめと書き込みを、同じ文の中で行う。ほかのインストールの行には触れない。
  - トークンの一意の制約は、確かめた行だけに効かせる (部分的な一意の索引)。確かめていない登録は何行あってもよく、どれにも送らない。
  - 引き継ぎは確かめのときに行う。確かめた側 (自分のアカウントの有効なインストール) が、同じトークンを確かめていたほかの行の確かめを外し、自分の行に記録する (1 つのバッチ)。確かめるには、トークンへの push を受け取る必要があるので (ADR-0008)、トークンを知っているだけの人は引き継げない。
  - 確かめを記録する関数は、確かめの記録 (code のハッシュ、指紋、環境、topic、期限) と突き合わせ、記録のトークンが今の端末と合うときだけ記録する。関数を呼ぶこと自体が引き継ぎになるので、記録 (証明) なしには呼べない形にした。トークンの指紋ごとの回数の制限もある (ADR-0008)。
  - APNs の無効の応答で止めるのは、送ったときのトークンの指紋と合うときだけ (間に入れ替わった新しいトークンを止めない)。
- **受け付けの記録**: 受け付けたあとに送れなかったら、記録を消して (`releaseEvent`)、送り手のやり直しを受け付ける。記録を残す期間は、送り手がやり直す期間より長くする。処理中のやり直しの扱いは ADR-0009 (記録に状態を持たせ、処理中のやり直しは 409、止まった処理中は 2 分で引き継ぐ)。
- **使わなくなった端末の行** (notification-service#14): 定期の掃除で、次の行を消す (確かめの記録も一緒に消す)。暗号化したトークンと指紋を、使わないまま残さないため。
  - APNs が無効と返した端末 (`invalidated`) で、30 日書き換えていないもの。同じインストールが登録し直せば有効に戻るので、少しのあいだは残す。
  - トークンを持っていることを確かめていない有効な端末で、30 日書き換えていないもの (確かめの push が届かなかった、ほかのインストールに引き継がれた、トークンを知っているだけの人の登録など)。アプリは起動のたびに登録し直すので、使っている端末なら書き換わる。
  - 利用者が止めた端末 (`disabled_by_user`) は消さない。消すと、次の起動の登録で、新しい有効な行ができ、止めた設定が戻ってしまう。インストールの取り消しとアカウントの削除で消える。鍵をなくして操作できなくなったインストールの行は、アカウントと一緒に、180 日使われなかったら消す (ADR-0010)。
  - 消すと、指紋の一意の索引 (確かめた行) からも外れる。
  - 「書き換えていない」は `updated_at` で見る。登録、確かめ、引き継ぎ、止める・戻す、APNs の無効は `updated_at` を書き換える。確かめの記録を置くこと (`createDeviceVerification`) は書き換えない (登録の直後にしか呼ばない)。
  - 探すときは、区切りのあいだで rowid の続きから読む。状態や時刻の索引は、起動のたびの登録の書き込みを増やすので置かない。1 回の掃除で、端末の行をほぼ 1 回読む (D1 の読み込みの見積もりは ADR-0009)。

## 採らなかった案

- **時刻を ISO 8601 の文字列にそろえる**: 生の SQL で `CURRENT_TIMESTAMP` と比べると、またずれる。DB で形を強制するには、長い CHECK が要る。
- **同じトークンを、最後に登録したインストールへ移す**: トークンを知っている人が、ほかの人の端末を乗っ取れる。
- **最初に登録したインストールに固定する**: 先取りした人が、本物の端末の登録を、ずっと妨げられる。
- **登録のときに、確かめていない行や使わなくなった行のトークンを譲る**: トークンを知っている人が登録をくり返すと、本物の端末の確かめを妨げ、利用者が止めた設定も消せる。確かめた行が残っていると、本物の端末が引き継げない。
- **端末を `enabled` の 1 つの値で持つ**: 利用者が止めたのか、APNs が無効と返したのかを区別できない。
- **外部キーを CASCADE にする**: 親の表を作り直す migration で、本番の子の行がすべて消える (`PRAGMA defer_foreign_keys` は確かめを遅らせるだけで、CASCADE の削除は止めない)。

## 影響

- D1 で親の表を作り直す migration は、drizzle-kit が出す `PRAGMA foreign_keys` が効かない (D1 はトランザクションの中で外部キーを確かめ続ける)。その場合だけ、作った SQL の先頭に `PRAGMA defer_foreign_keys = on`、末尾に `PRAGMA defer_foreign_keys = off` を置き、途中の `PRAGMA foreign_keys` の行はすべて消す。SQLite は、遅らせた外部キーの違反を off に戻すまで数え続け、`DROP TABLE` は親の行を消すので違反を数える。末尾の off がないと、コミットのときに失敗する (D1 は理由を出さず `internal error` と返す)。外部キーが NO ACTION なので、行は残る (AGENTS.md)。
- テスト (`apps/api/test/db/migrations.test.ts`) は、0000 の形で入れたデータが、後の migration を当てたあとも残ること、`PRAGMA foreign_key_check` で親のない子の行がないことを確かめる。
- CI で `drizzle-kit generate` を動かし、`schema.ts` と migration がずれていないことを確かめる。
- 確かめ (`verified_at`) を記録する API ができるまで、どの端末にも送らない。トークンを持っていることの確かめは、リリースの前に要る (ADR-0008。push を送る仕組みは APNS-002)。
