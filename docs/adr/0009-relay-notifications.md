# ADR-0009: 中継の受け付けと、端末へ送る流れ

Status: Accepted / 2026-11-04

## 背景

設計書 v1.1 の §4 は、利用者の Worker が中継の資格情報で `POST /v1/notifications` を呼び、運営の API が資格情報のアカウントの端末へ送る形を求めている。本文の大きさの上限、イベントの種類の許可リスト、UTC の時刻、アカウントごとの回数の制限、`event_id` による重複の除去が要る。DB-001 からは、処理中のやり直しの扱いと、受け付けの記録が消えた後のやり直し (リプレイ) を、イベントの時刻の新しさで拒むことが引き継がれている (ADR-0004、ADR-0005)。

## 決定

### 受け付ける本文

- 送り先のアカウントは、中継の資格情報 (`requireRelayCredential`、ADR-0007) だけで決める。
- 本文は次の 4 つだけを受け、ほかのキーがあれば 422 にする (`account_id`、`x_user_id`、`apns_token`、題や本文、URL を受けない)。
  - `event_id`: `[A-Za-z0-9._:-]` の 1〜128 文字。
  - `type`: 許可リスト (`mention`、`reply`、`quote`、`retweet`、`like`、`follow`)。
  - `post_id`: 数字だけ (先頭は 0 でない、19 桁まで。X の ID は 64 ビットの整数)。ツイートを指す種類 (`follow` 以外) では要り、`follow` では受けない。
  - `occurred_at`: UTC (末尾が `Z`) の RFC 3339 の時刻。
- `occurred_at` は、5 分より先のもの (時計のずれを越えるもの) と、受け付けの記録を残す期間 (7 日) から掃除の間隔 (1 日) と時計のずれ (5 分) を引いたものより古いものを、422 で拒む。記録が消えた後のやり直しを、記録では防げないため。
- 本文の大きさの上限 (4 KiB) は、ほかの入口と同じ (ADR-0006)。

### 重複の除去と処理中のやり直し

- 受け付けの記録 (`delivery_dedup`) の鍵 (`event_key`) は、アカウントと `event_id` の HMAC-SHA256。
  - `event_id` に X の ID などが入りうるので、生の値も、鍵のないハッシュも DB に置かない。`mention:<ツイートの ID>` のような推しやすい値は、鍵のないハッシュでは、候補をハッシュにして確かめられる。
  - アカウントを入れ、同じ `event_id` でもアカウントごとに違う鍵にする (アカウントどうしを結び付けさせない)。
  - 鍵は、デバイストークンの指紋の鍵 (入れ替えない。ADR-0005) を使い、頭の文 (`twitter-studio/event-key/v1`) で用途を分ける。
  - 長さが決まるので、APNs の `apns-collapse-id` (64 バイトまで) にも使える。
- 記録には、状態 (`processing`、`done`)、最後に書いた時刻、リースの印 (`lease_id`) を持たせる。時刻はサーバーの時刻を書く (送り手の時刻で、記録を早く消させない)。
- 先に記録の状態を 1 行だけ読み、済んだ重複と処理中のやり直しには、1 日の上限より先に答える (上限に届いた後も、やり直しの答えを変えない)。受け付けるかは、記録を書く 1 文で決め直す (読んだ後にほかの要求が先に受け付けたとき)。
- 初めてのイベント: 1 日の数を数え、記録を `processing` で置き、端末へ送り、`done` にして 202 (`status: "accepted"`)。
- 送り終えたイベント (`done`) のやり直し: 送らずに 202 (`status: "duplicate"`)。
- 送っている途中 (`processing`) のやり直し: 409 と `Retry-After: 30`。
- `processing` のまま 2 分を過ぎた記録は、Worker が途中で落ちたものとみなし、やり直しで引き継いで送る。
- 受け付けと引き継ぎのたびに、リースの印を変える。済みにする (`completeEvent`) のと、消す (`releaseEvent`) のは、今の印を持つ `processing` の記録だけ。引き継がれた後の前の要求は、記録を消すことも済みにすることもできない (消すと、3 回目の要求も受け付けて、もう 1 回送ってしまう)。
- 端末へ送る時間は 60 秒まで (リースの 2 分より短い)。送り手 (`PushGateway`) には、残りの時間の `AbortSignal` を渡す。時間を過ぎたら、残りの端末には送らない。
- 受け付けの記録を書けないとき (D1 など): 503 と `Retry-After: 60`。
- 送る途中で失敗したとき (D1、鍵の設定など): 今の印の記録を消し、503 と `Retry-After: 60` を返す。途中まで送っていたら、やり直しで同じ通知が 2 回届きうる (配信は少なくとも 1 回。ADR-0001 §5)。
- 送った後に記録を済みにできないとき: 送ったので 202 を返し、ログに出す。記録は処理中のまま残り、リースが切れた後のやり直しで、もう 1 回送りうる。
- 済みにしようとしたら、リースが切れてほかの要求に引き継がれていたとき: 済みにせず (引き継いだ要求が送って済みにする)、`relay_lease_lost` をログに出す。同じ通知が 2 回届く。

### 端末へ送る

- 送り先は、アカウントの、有効で、トークンを持っていることを確かめた端末 (`listActiveDevices`、ADR-0004、ADR-0008)。暗号文を読めない端末は飛ばし、ほかの端末には送る。
- 送り先の端末がなければ、受け付けの記録を書かずに 202 を返す (D1 の書き込みを使わない)。
- 送るのは `PushGateway` (設計書 §5)。APNs へ送る部分は APNS-002 で作る。それまでは送らない (確かめた端末もない)。
- 端末ごとの結果:
  - `invalid_token` (APNs の 410、BadDeviceToken): 端末を止める (`invalidateDevice`)。
  - `retry_later`、`failed`: 今は中継の入口ではやり直さず、イベントは `done` にする (その通知は届かない)。やり直しの仕組み (Queues か、限りのあるやり直し) は APNS-002 で決める。
  - 結果の数だけをログに出す (トークン、端末の ID は出さない)。送れなかった端末 (読めない暗号文、`failed`、`retry_later`、時間切れ) があれば error で出し、運営が気づけるようにする (鍵の入れ替えの誤りなど)。
- 通知の中身は、中身を運ばない一般的な文 (ADR-0001 §4) で、アプリの訳 (`loc-key`) で出す。
  - 形: `{"aps":{"alert":{"loc-key":"You have a new notification."},"sound":"default"},"event_type":"mention","post_id":"…"}`。
  - 送り手の文、題、URL は入れない。ほかのアプリや運営を装った文を出させないため。
  - アプリは `loc-key` の訳を持ち、`post_id` を確かめてから、X の決まった画面だけを開く (IOS-001)。iOS は `loc-key` をアプリ本体の bundle から引くので、訳はアプリのターゲットに置く (Tweetbot の画面の訳がある TweetbotUI パッケージではない)。

### 回数の制限

- アカウントごと (`RELAY_RATE_LIMITER`、`relay:<アカウントの ID>`、1 分に 30 回)。中継の資格情報を確かめた後、本文を確かめる前に数える (形の違う本文も数える)。namespace は 1004 (ADR-0006 の台帳)。
- アカウントごとの 1 日の上限 (1,000 件)。新しいイベント (記録がないもの) のときだけ、アカウントごとに 1 行の数え役 (`relay_usage`) を 1 文で増やし、超えたら 429 と、次の UTC の 0 時までの秒数の `Retry-After` を返す。
  - 数える日は UTC の 0 時から。D1 の無料のプランの枠が戻る時刻にそろえ、1 つの日に上限の 2 日分が入らないようにする。
  - 止まった処理中の記録の引き継ぎは数えない (最初に受け付けたときに数えている)。上限の後でも引き継いで送る。
  - 送れずに記録を消したイベントのやり直しは、もう 1 回数える (数を戻さない)。多めに数えるだけで、上限を越えることはない。
  - Rate Limiting のバインディングで選べる期間は 10 秒か 60 秒だけなので、1 日の上限は DB で持つ。
  - 受け付けの記録の数を数えると、上限に近いアカウントの要求のたびに、上限の数だけ行を読み、D1 の読み込みの枠を使い切る (再レビューで分かった)。数え役なら、読むのも書くのも 1 行で、数えてから書くまでの隙間もない。
- D1 の書き込みの見積もり: 1 件の受け付けで、数え役 (1 行)、記録の挿入 (表と主キーの索引で 2 行)、済みにする (1 行)、7 日後の掃除 (2 行) の、およそ 6 行を書く。1 つのアカウントが上限まで使うと 1 日に約 6,000 行で、無料のプランの枠 (1 日 10 万行) は、上限まで使うアカウントが 16 ほどで尽きる。
- D1 の読み込みの見積もり: 端末のあるアカウントの 1 回の要求で、およそ 10 行を読む (受け付け 11〜12 行、重複 8 行、1 日の上限の 429 で 9 行、端末なしで 5 行)。1 分の上限 (30 回) で送り続けると、1 日に約 40 万行で、無料のプランの枠 (1 日 500 万行) は、上限で送り続けるアカウントが 12 ほどで尽きる。
  - 1 分の上限を越えた要求も、資格情報を確かめてから 429 になるので、1 回に約 4 行を読む。この要求の数は 1 分の上限では縛られず、Workers の要求の数の枠でしか縛られない。
  - 定期の掃除は、使わなくなった端末を探すのに毎日、端末の行をほぼすべて 1 回読み (ADR-0004)、使われなくなったアカウントを探すのに、アカウントごとに 2〜3 行を読む (ADR-0010)。
- どちらかの枠が尽きると、UTC の 0 時まで、すべてのアカウントの登録と中継が止まる。招待制のあいだは足りるとし、テストをする人が増える前か、登録を開く前 (AUTH-003) に、有料のプランか、全体の上限を決める。
- 定期の掃除は、掃除ごとに Cron を分け (1 回の呼び出しで D1 に投げる問い合わせは、無料のプランで 50 まで。バッチは 1 回と数える)、それぞれ 45 問い合わせまでにする。受け付けの記録は 1 日 4.5 万件まで消す (アカウントごとの上限の 45 アカウント分)。受け付けの記録は、索引を使わず rowid の順 (ほぼ受け付けた順) に読んで探す。アカウントの順の索引で読むと、区切りごとに、前のアカウントの新しい行を読み直す。受け付けた時刻の索引は置かない (受け付けのたびの書き込みが増えるため)。
- 資格情報を確かめる前 (偽のトークンで D1 を引かせる要求) は、まだ数えない。利用者の Worker からの要求は Cloudflare の IP から届き、多くの利用者で同じ IP になりうると考えている。そのため、IP ごとの制限 (`CLIENT_RATE_LIMITER`) はそのままでは付けない。実際にどの IP が `CF-Connecting-IP` に入るかを、デプロイした Worker どうしで確かめてから決める (APNS-001 でデプロイするときに確かめる)。それまでの危険は、D1 の読み込み (無料のプランで 1 日 500 万行) と Workers の要求の数を使われること。

### 送り手 (利用者の Worker) との約束

- 409、429、503、500 は、`Retry-After` の秒数 (なければ 60 秒) を待ってやり直す。
- 401、403、413、415、422 はやり直さない (401 は資格情報を入れ替えたときなので、利用者に知らせる。ADR-0007)。
- やり直しは、イベントの時刻から 1 日以内に終える (受け付けの記録を残す期間と、イベントの古さの上限の内側にするため)。

## 採らなかった案

- **送り手の題や本文を、そのまま通知に出す**: 送り手が、ほかのアプリや運営を装った文や、外部の URL を送れる。中身を運ばない文を既定にする設計書の決定とも合わない。
- **受け付けの記録に、送り手の `occurred_at` を書く**: 送り手が記録を過去の日付にして、早く消させ、やり直しで 2 回送らせられる。
- **処理中のやり直しに 202 を返す**: 1 回目が失敗して記録を消したとき、もう誰もやり直さず、通知が届かない。
- **処理中のやり直しに 503 を返す**: やり直す点は同じだが、送れなかった (503) と、送っている途中 (409) を、送り手のログで分けられるようにする。
- **漏れた中継の資格情報で、使われそうな `event_id` を先に送って、正規の通知を重複として止める**: 防げない (送り手が決める ID なので)。資格情報を入れ替えれば止まる (ADR-0007)。`event_id` を推しにくくするのは、送り手 (USER-001) の作り方で行う。
- **端末ごとの `retry_later` で、イベント全体を 503 にする**: 送れた端末にも、やり直しで 2 回届く。端末ごとのやり直しは、APNs へ送る部分 (APNS-002) で持つ。

## 影響

- APNs へ送る部分 (APNS-002) は、`PushGateway` を作り、`createApp` に渡す。端末ごとのやり直しと、`apns-collapse-id` (`event_id` を 64 バイトに収める) も決める。
- 利用者の Worker (USER-001) は、上の約束のとおりにやり直す。
- アプリ (IOS-001) は、`You have a new notification.` の訳を持ち、`event_type` と `post_id` を確かめてから開く。
