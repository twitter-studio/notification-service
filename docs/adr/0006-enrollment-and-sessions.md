# ADR-0006: 端末の登録とセッション

Status: Accepted / 2026-11-04

## 背景

設計書 v1.1 の §3 (手順 1〜3) と §4 は、チャレンジによる登録、鍵を持っていることの確かめ、短命のセッション、1 回だけ見せる中継の資格情報を求めている。App Attest は、使えるなら登録に結び付けるとしたうえで、安全に作れないなら試作のあいだは登録をテスト用のアカウントに限り、確かめていない登録をリリースを止める条件として書くことを求めている (§3)。

## 決定

### 端末の鍵と署名

- **端末の鍵**: ECDSA P-256。iOS の Secure Enclave (CryptoKit の `SecureEnclave.P256.Signing.PrivateKey`) で作る。
  - 公開鍵は X9.63 の非圧縮の点 (65 バイト、0x04 で始まる。CryptoKit の `x963Representation`)。
  - 署名は r‖s の 64 バイト (CryptoKit の `rawRepresentation`)。署名の対象は文を SHA-256 にしたもの (CryptoKit の `signature(for:)` と同じ)。CryptoKit で作った公開鍵と署名を、テストのフィクスチャに置いている (`test/security/installation-key.test.ts`)。
  - Simulator には Secure Enclave がない。開発のビルドに限り、Keychain に置いたソフトウェアの鍵 (`P256.Signing.PrivateKey`) を使ってよい。サーバーからは区別できないので、確かめていない登録として扱う (下の「試作のあいだの制限」)。
- **バイト列の書き方**: 公開鍵、署名、チャレンジの中身は Base64URL で、余白の `=` を付けない。最後の文字の使わないビットは 0 にする。これ以外の書き方 (`=` 付き、`+` と `/`、使わないビットが 0 でないもの) は、同じバイト列でも受けない。
  - 公開鍵は文字列のまま DB に置き、同じ鍵かを文字列で比べる。書き方の違いを受けると、同じ鍵で別のアカウントを作れ、止めたアカウントの 403 もすり抜けられる。
  - iOS の `base64EncodedString()` は標準の Base64 (`+`、`/`、`=` 付き) を返すので、アプリで `-`、`_` に置き換え、`=` を除く。
- **署名する文**: 用途、チャレンジ、署名の対象を改行で並べる。用途を入れて、ほかの用途の署名を使い回させない。
  - 登録: `twitter-studio/enroll/v1\n<チャレンジ>\n<公開鍵>`
  - セッション: `twitter-studio/session/v1\n<チャレンジ>\n<インストールの ID>`

### チャレンジ

- サーバーの秘密 (`CHALLENGE_SIGNING_KEY`) の HMAC で署名した値 (`c1.<内容>.<HMAC>`)。内容は nonce、用途 (enroll、session、中継の資格情報の入れ替えの relay_credential (ADR-0007)、端末の登録の device (ADR-0008))、期限 (5 分)。
- 出すときには DB に書かない。名前を名乗らない呼び出しで、D1 の書き込み (無料のプランで 1 日 10 万行) を使わせないため。
- 使ったときに、その nonce を `used_challenges` に記録する。登録やセッションと同じバッチの先頭で書くので、同じチャレンジの 2 回目は、何も作る前に 409 になる。署名が違うときは記録しないので、同じチャレンジを正しい署名で使い直せる。
- 記録は、期限からサーバーどうしの時計のずれの幅 (1 分) を過ぎたら、定期の掃除で消す。時計の遅れたサーバーがまだ期限内として受けるうちに記録を消すと、使い回せてしまうため。
- `CHALLENGE_SIGNING_KEY` は、デバイストークンの鍵 (ADR-0005) と別の値にし、環境ごとに作る。読むときに、`DEVICE_TOKEN_KEY_CHECKS` の確かめの値と比べ、同じ鍵なら失敗にする。確かめの値が空のあいだ (本番の鍵を作る前) は、この確かめは効かない。`DEVICE_TOKEN_KEY_CHECKS` が壊れているときは、チャレンジも作れない (閉じる側に倒す)。

### 登録 (`POST /v1/enrollments`)

- 招待のコード、チャレンジ、公開鍵、署名で、アカウント、インストール、中継の資格情報、セッションを 1 つのバッチで作る (201)。中継の資格情報 (`tsr_…`) は、この応答でだけ返す。資格情報の ID (`relay_credential_id`) も返し、入れ替えと取り消し (AUTH-002) で使う。
- 同じ公開鍵で登録し直したときは、鍵の持ち主の状態で決める。
  - 有効なインストール: 前の応答を受け取れなかったなど。署名で鍵を持っていることを確かめたうえで、前のアカウントのセッションだけを返す (200)。中継の資格情報は返さない。作り直すには、入れ替え (AUTH-002) を使う。同時に 2 回呼んでも、アカウントは 1 つだけできる。
  - 取り消したインストール、止めたアカウント: 403。
  - 消したアカウント: インストールの行も消してあるので、新しいアカウントとして登録する (201)。
- **鍵をなくしたとき** (アプリを消した、端末を替えた、Secure Enclave の鍵が消えた): 新しい鍵で、新しいアカウントとして登録し直す。前のアカウントには、X の ID、APNs のトークン、送り手が名乗る UUID で結び付けない (ADR-0001 §2)。
  - 利用者は、新しい中継の資格情報を、自分の Worker に入れ直す。
  - 同じ APNs のトークンを新しいインストールで確かめると、端末の行は新しい方へ移る (ADR-0004) ので、前のアカウントの資格情報で送っても、その端末には届かない。
  - 前のアカウントは、持ち主が鍵で操作できないまま残る。同じ端末で同じ APNs のトークンを新しいインストールが確かめると、前の端末の行は確かめを外されて送り先から外れ、有効な行なら 30 日で消える (notification-service#14)。利用者が止めていた行と、端末を替えて引き継がれなかった行 (確かめたまま) は残る。これらは、アカウントと一緒に、180 日使われなかったら消す (ADR-0010)。

### セッション

- 1 時間の bearer (`tss_…`)。端末の鍵でチャレンジに署名して作り直す (`POST /v1/sessions`)。設計書の API の一覧には作り直す入口がないので、ここで足す。
- 確かめるとき (`requireSession`) は、期限、取り消し、インストールとアカウントが有効なことを見る。
- 1 つのインストールが持てるセッションは 5 つまで。作るときに、新しいものから 4 つを残して、ほかを消す (期限切れ、取り消し済みも含めて)。
- インストールを取り消すとき、アカウントを消すときは、セッションの行も消す。
- インストールがないときも、決まった鍵 (P-256 の生成元の点) で署名を確かめる。かかる時間で、インストールの ID があるかを探らせない。

### トークンの置き方

- セッションと中継の資格情報は 32 バイトの乱数。DB には SHA-256 だけを置く (鍵のない SHA-256 でも、乱数なので総当たりで探せない)。頭の印 (`tss_`、`tsr_`) で、秘密の走査で見つけやすくする。
- `/v1` の応答には `Cache-Control: no-store` を付け、途中の cache に秘密を残させない。

### 回数の制限

- Workers の Rate Limiting のバインディングで数える (`wrangler.jsonc` の `ratelimits`)。超えたら 429 と `Retry-After: 60` を返す。
  - 接続元の IP ごと (`CLIENT_RATE_LIMITER`): チャレンジ、登録、セッションの作り直しを合わせて、1 分に 20 回 (1 回の登録で 2 回)。この入口には、IP のほかに数える単位がない (Rate Limiting の文書は、IP は多くの人で共有されうるとして勧めていない)。
    - IPv6 は /64 にまとめて数える。回線や VPS は 1 人に /64 以上を配るので、アドレスを変えるだけで越えさせないため。家庭の回線は /56 や /48 を配ることも多く、その人は /64 を変えて越えられる。書き込みに届くのは招待のコードを持つ人だけなので、今は /64 で足りるとし、越える人が出たら /48 で数える 2 つ目の制限を足す。
    - IPv4 を写した IPv6 (`::ffff:0:0/96`) と NAT64 (`64:ff9b::/96`) は、書き方によらず IPv4 として数える。前の 64 ビットが 0 のアドレス (IPv4 互換、ループバックなど) はまとめない。まとめると、ほかの書き方で届いた IPv4 の人が 1 つの単位を分け合い、1 人で全員の登録を止められる (Cloudflare は IPv4 の人を `192.0.2.1` の形で送るので、今は届かない)。
  - インストールごと (`INSTALLATION_RATE_LIMITER`): 署名を確かめたあとにセッションを作るもの (セッションの作り直しと、同じ鍵での登録し直し) を合わせて、1 分に 5 回。署名の後に数えて、ほかの人にその枠を使わせない。中継の資格情報の入れ替えと取り消しも、このバインディングで、別の単位として数える (ADR-0007)。
  - `namespace_id` は、Cloudflare のアカウントの中で共有される。notification-service は 1001、1002、1003 (ADR-0008)、1004 (ADR-0009) を使う。同じアカウントに置くほかの Worker (staging、オーナーが試す notification-worker など) には、別の番号を付ける。
- 数は Cloudflare の場所ごとのおおよその数で、少し超えることがある。総当たりと、D1 の書き込みの使い切りを遅らせるためのもの。招待のコードの総当たりは、コードの長さ (128 ビット以上) で防ぐ。
- 手元のテスト (Miniflare) でも数える。テストは要求ごとに違う IP (`CF-Connecting-IP`) を付ける。
- 無料のプランで使えるかは、2026-11 の公式の文書 (バインディングの説明、料金、GA の告知) に書かれていない。本番の Worker を作る前に、オーナーが確かめる (`wrangler deploy --dry-run` では分からない)。

### 試作のあいだの制限

- 登録には、秘密 `ENROLLMENT_INVITE_CODE` と同じ招待のコードが要る。秘密がない、または 22 文字 (16 バイトの Base64URL) より短いときは、登録を受け付けない。短いときは、isolate ごとに 1 回ログに出す (値は出さない)。
- 受け付けていないときと、コードが違うときは、同じ 403 にする。受け付けていないときも比べる手間をかけ、応答の文と時間で、秘密を置いたかを探らせない。
- コードは 16 バイト以上の乱数で作り (`node -e 'console.log(crypto.randomBytes(16).toString("base64url"))'`)、オーナーがテストをする人に配る。アプリには埋め込まない (アプリから取り出せるため)。利用者が入力する。
- App Attest を確かめるまで (AUTH-003、notification-service#15)、この制限を外さない。確かめていない登録が残るあいだは、リリースしない。

### エラー

- 本文が JSON として読めないときは 400、`application/json` でないときは 415、4 KiB を超えるときは 413。
- 入力の誤りは 422。どの値が違うかは返さない。
- チャレンジや署名の誤りは 401。インストールがないときと署名が違うときは、同じ応答にする。
- 招待の誤り、登録を受け付けていないとき、取り消したインストールや止めたアカウントの鍵は 403。
- チャレンジの使い回しは 409。回数の制限を超えたら 429。

## 採らなかった案

- **チャレンジを、出すときに DB に置く**: 名前を名乗らない呼び出しのたびに書き込みが要り、書き込みを使い切られる。
- **回数を D1 で数える**: 名前を名乗らない呼び出しのたびに書き込みが要る (チャレンジを DB に置く案と同じ)。正確に数えられるが、この用途 (総当たりと使い切りを遅らせる) には、おおよその数で足りる。
- **署名を DER の形で受ける**: iOS の `SecKeyCreateSignature` は DER を返すが、Web Crypto は r‖s を受ける。CryptoKit の `rawRepresentation` ならそのまま渡せる。
- **セッションを、署名した自己完結のトークン (JWT など) にする**: 取り消しを即座に効かせられない。D1 に置けば、取り消しと削除がすぐ効く。
- **テストをする人ごとの招待のコード (D1 にハッシュを置く)**: 配った人ごとに止められるが、表と管理の手順が要る。テストをする人が少ないあいだは、1 つのコードを入れ替えて足りる。人が増えたら考える。

## 影響

- アプリ (IOS-001) は、Secure Enclave で鍵を作り、上の形 (`=` なしの Base64URL) で公開鍵と署名を送る。招待のコードは利用者が入力する。
- 秘密 `CHALLENGE_SIGNING_KEY` と `ENROLLMENT_INVITE_CODE` は、本番の Worker を作るときにオーナーが置く。
- 本番の Worker を作る前に、Rate Limiting のバインディングが使えるプランかを確かめる。
- 定期の掃除で、期限を過ぎた使ったチャレンジとセッションの記録も消す。
