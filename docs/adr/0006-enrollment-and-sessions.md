# ADR-0006: 端末の登録とセッション

Status: Accepted / 2026-11-04

## 背景

設計書 v1.1 の §3 (手順 1〜3) と §4 は、チャレンジによる登録、鍵を持っていることの確かめ、短命のセッション、1 回だけ見せる中継の資格情報を求めている。App Attest は、使えるなら登録に結び付けるとしたうえで、安全に作れないなら試作のあいだは登録をテスト用のアカウントに限り、確かめていない登録をリリースを止める条件として書くことを求めている (§3)。

## 決定

- **端末の鍵**: ECDSA P-256。iOS の Secure Enclave (CryptoKit の `SecureEnclave.P256.Signing.PrivateKey`) で作る。
  - 公開鍵は X9.63 の非圧縮の点 (65 バイト、0x04 で始まる) の Base64URL。
  - 署名は r‖s の 64 バイト (CryptoKit の `rawRepresentation`) の Base64URL。署名の対象は文を SHA-256 にしたもの (CryptoKit の `signature(for:)` と同じ)。
- **署名する文**: 用途、チャレンジ、署名の対象を改行で並べる。用途を入れて、ほかの用途の署名を使い回させない。
  - 登録: `twitter-studio/enroll/v1\n<チャレンジ>\n<公開鍵>`
  - セッション: `twitter-studio/session/v1\n<チャレンジ>\n<インストールの ID>`
- **チャレンジ**: サーバーの秘密 (`CHALLENGE_SIGNING_KEY`) の HMAC で署名した値 (`c1.<内容>.<HMAC>`)。内容は nonce、用途 (enroll か session)、期限 (5 分)。
  - 出すときには DB に書かない。名前を名乗らない呼び出しで、D1 の書き込み (無料のプランで 1 日 10 万行) を使わせないため。
  - 使ったときに、その nonce を `used_challenges` に記録する。登録やセッションと同じバッチの先頭で書くので、同じチャレンジの 2 回目は、何も作る前に 409 になる。記録は期限が過ぎたら定期の掃除で消す。
- **登録** (`POST /v1/enrollments`): 招待のコード、チャレンジ、公開鍵、署名で、アカウント、インストール、中継の資格情報、セッションを 1 つのバッチで作る (201)。中継の資格情報 (`tsr_…`) は、この応答でだけ返す。
  - 同じ公開鍵で登録し直したとき (前の応答を受け取れなかったなど) は、署名で鍵を持っていることを確かめたうえで、前のアカウントのセッションだけを返す (200)。中継の資格情報は返さない。作り直すには、入れ替え (AUTH-002) を使う。
- **セッション**: 1 時間の bearer (`tss_…`)。端末の鍵でチャレンジに署名して作り直す (`POST /v1/sessions`)。設計書の API の一覧には作り直す入口がないので、ここで足す。
  - 確かめるとき (`requireSession`) は、期限、取り消し、インストールとアカウントが有効なことを見る。
  - インストールを取り消すとき、アカウントを消すときは、セッションの行も消す。
- **トークンの置き方**: セッションと中継の資格情報は 32 バイトの乱数。DB には SHA-256 だけを置く (鍵のない SHA-256 でも、乱数なので総当たりで探せない)。頭の印 (`tss_`、`tsr_`) で、秘密の走査で見つけやすくする。
- **試作のあいだの制限**: 登録には、秘密 `ENROLLMENT_INVITE_CODE` と同じ招待のコードが要る。秘密がなければ登録を受け付けない (403)。オーナーがテストをする人に配る。App Attest を確かめるまで (AUTH-003、notification-service#15)、この制限を外さない。確かめていない登録が残るあいだは、リリースしない。
- **エラー**:
  - 入力の誤りは 422。どの値が違うかは返さない。
  - チャレンジや署名の誤りは 401。インストールがないときと署名が違うときは、同じ応答にする (インストールの ID があるかを探らせない)。
  - 招待の誤りと、登録を受け付けていないときは 403。
  - チャレンジの使い回しは 409。
  - 本文が 4 KiB を超えるときは 413。

## 採らなかった案

- **チャレンジを、出すときに DB に置く**: 名前を名乗らない呼び出しのたびに書き込みが要り、回数の制限なしでは、書き込みを使い切られる。
- **Workers の Rate Limiting で、チャレンジの呼び出しを制限する**: 無料のプランで使えるか、手元のテストで動くかを、2026-11 の公式の文書で確かめられなかった。数え方も、場所ごとのおおよその数になる。チャレンジを DB に書かない形にしたので、今は要らない。
- **署名を DER の形で受ける**: iOS の `SecKeyCreateSignature` は DER を返すが、Web Crypto は r‖s を受ける。CryptoKit の `rawRepresentation` ならそのまま渡せる。
- **セッションを、署名した自己完結のトークン (JWT など) にする**: 取り消しを即座に効かせられない。D1 に置けば、取り消しと削除がすぐ効く。

## 影響

- アプリ (IOS-001) は、Secure Enclave で鍵を作り、上の形で公開鍵と署名を送る。
- 秘密 `CHALLENGE_SIGNING_KEY` と `ENROLLMENT_INVITE_CODE` は、本番の Worker を作るときにオーナーが置く。
- 定期の掃除で、期限を過ぎた使ったチャレンジとセッションの記録も消す。
