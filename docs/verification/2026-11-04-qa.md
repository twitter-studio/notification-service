## 実Queueの障害試験

Appleへ送るtransportだけをプロセス内の合成応答へ差し替え、同じApnsClient / ApnsPushGatewayを使った。実際の鍵・端末トークン・X接続はコピーしていない。QA専用のschemaからmigrationを生成した。D1の単一行でcampaignを1回に制限し、認証・回数制限・CPU1秒・2時間以内の期限を付けた。

| ケース           | 実測                                                               |
| ---------------- | ------------------------------------------------------------------ |
| 通常200          | 1回で終了                                                          |
| 429から回復      | 429→200。間隔 70.087 秒                                            |
| 503打ち切り      | 503→503→503。間隔 941.733 秒 / 1977.73 秒。初回を含め3回で打ち切り |
| 停止・失効・更新 | 初回429の後に状態を変え、実Queueでは再送せず破棄                   |
| 400/410          | 端末がinvalidatedとなり、Queueへ入らない                           |

送信処理を4 isolateで観測し、各JWTのiatを検査した。これは合成応答下での発行と再送の確認であり、Appleの複数isolateに対するレート制限や本番topicの確認には置き換えない。実機表示の証拠は上の別試験による。

最終Queueの件数・サイズは0。GraphQLが報告したbillable operationsは16。5 write + 6 read + 5 deleteという試験の処理と対応する。Queueの保存期間は86400秒で作成し、試験終了後にconsumer・Worker・Queue・DBを削除した。

## 小規模負荷と費用

結果参照APIを20要求・並列5で1回実行し、20件すべて200だった。この入口は3つのD1集計を読む。通常の中継API、署名検証や送信を連続で流す性能測定ではなく、最大スループットや招待数拡大の性能保証にはしない。

| 報告値                                        | 値                     |
| --------------------------------------------- | ---------------------- |
| Worker invocations / runtime errors           | 75 / 0                 |
| CPU合計 / 最大                                | 433.974 ms / 47.778 ms |
| D1 rows read / written                        | 2561 / 240             |
| D1保存量                                      | 188416 bytes           |
| Queue billable operations / 最大message bytes | 16 / 559               |

CloudflareのGraphQL集計で、setup・migration・試験・観測を含む専用リソースの窓である。Workerは削除前の 17:47:53〜18:43:19 JST の取得値を使い、D1とQueueは削除後も取得できた 17:47:53〜18:45:30 JST の値を使う。Workerの削除後はその集計が空になった。集計反映には遅れがあり、要求数の突き合わせに使う完全な台帳ではない。adaptive datasetの報告値であり、最終請求額やHTTPの正確なカウンターと同一視しない。意図的なAPNsの503はWorker runtime errorとは別の値。秘密やraw logsは保存していない。合成APNs処理のログのmetadataをメモリー内で比較し、今回の合成秘密の一致は0だった。比較結果だけを残した。

Workers Paidは月1000万要求・CPU3000万ms、D1は月250億reads・5000万writes・5GB、Queuesは月100万operationsを含む。枠はアカウント全体で共有し、今回の少量だけから永久に無料とは判断しない。超過の単価は、Worker要求$0.30/百万、CPU$0.02/百万ms、D1 reads $0.001/百万・writes $1/百万、Queue $0.40/百万。既存プランは変更していない。

1端末・1日1000イベント・30日すべて再送2回なら、Queueは12万operations。10アカウントなら120万で、他の使用量がなく含まれる100万を使える場合の超過分は$0.08。D1はADR-0009の受け付け約6writes/eventに、再送時の権限と端末の読み直しを足す。実際の行数は索引と走査で変わるため、応答件数から算出しない。今回は上の実測だけを受け入れ、招待数を増やす前に通常の中継経路で件数・CPU・DB予算を再測定する。

## 監視と見つけた修正

- PR #33: 許可項目だけの構造化ログと監視CLI。外部例外名・アカウントIDをログから除いた。
- PR #34: query秘匿を実環境で照合。method/URL/path自体は残り、任意pathの完全匿名化を証明したとはしない。
- PR #36: SQLのJSON条件付き集計の制約を数値カウンターで避け、4系統のnative監視とQueueの5分Cronを接続した。別用途の既存policyは維持。
- PR #37/#38: 隔離した障害試験を追加。モジュール初期化時の乱数生成による配置拒否を直し、配置して検証した。
- PR #40 / #39: Queueの概算件数が0・bytes559・最古時刻ありとなる実例を受け、bytesも使う判定へ修正。検証済み2値からbacklog_presentを作り、SQLの再帰制限を避ける。件数やbytesを捏造しない。

運営の稼働versionは `61bd8f46-aaa7-49cf-bdcf-85449446d8b5`。新しい数値を含むCronログとcritical SQLの200を確認した。有効状態・宛先を保持し、4系統の監視を継続する。メールのテスト送信はオーナーが実受信を確認済み。隔離試験の打ち切り後、同じcritical SQLをQAのWorkerだけに絞ると判定値1となった。native policyの対象は変えず、追加メールは送っていない。native閾値による実配送の試験とは区別する。監視定義は稼働コードと対応させる。

## 残るリリース条件
