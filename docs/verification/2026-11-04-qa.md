## 費用の試算と制限

既存の契約は Workers Paid。プランの変更・招待人数の拡大は行わない。料金は同日の公式資料で確認した。含まれる枠はアカウント内のほかの Worker と共有する。以下は課金の上限保証や負荷測定ではない。

1件が64KB未満で、初回送信が一時障害となり、consumer を2回呼んで終了する場合、Queue は write 1 + read 2 + delete 1 = 4 operations。1アカウント・1端末が1日1000イベント、30日すべて一時障害なら12万operations、10アカウントなら120万operations。Paid の月100万operationsの含まれる枠を越える20万operationsは $0.08。実際には他の Queue の使用量も足す。端末数が増えると掛け算になる。

D1 の既存の見積もりは ADR-0009 を使う。受け付けだけで約6 writes/event、再送ごとの権限・端末読み直しが追加される。Paid は月250億 reads、5000万 writes、保存5GBを含む。実際に読む行数は索引と走査によるため、応答件数から計算しない。meta / GraphQL / dashboard で測る。

Workers は要求数だけでなく CPU、Queue consumer、定期 query とログの使用量も数える。通常配信に成功した少数の要求だけから月額を推定しない。未認証で D1 を読ませる要求はアカウントの日次枠では止まらないため、招待を広げる前に対策・予算を確定する。

## 実環境での実行手順と停止条件

1. 既存の sandbox 更新の前に、コード・独立レビュー・CIを通す。Queue の待機数とサイズを確認する。secret、topic、DB schema、アプリの通知アカウントを変更しない。
2. 固定 health / 未認証 API の少数リクエストで、status とサーバー生成 request ID を照合する。テスト用の canary を query・独自ヘッダー・不正な bearer へ入れ、対象のログだけを閲覧し、Cloudflare が付ける metadata も含めて残っていないか確認する。本物の秘密を canary にしない。raw log の出力・保存・Tail はしない。
3. 5分の範囲で HTTP status / APNs status / 再送打ち切りだけを集計し、Queue の backlog / oldest age と合わせる。取得できなければ `invalid` として止める。サンプリングや集計の対象が不明な数値を正確なカウンターとみなさない。
4. `check-alerts` の正常・故障・欠損入力を実行する。監視を有効化するときは、対象アカウントの dataset、権限、評価間隔、受信先を確定し、テスト警報が届くことまで確認する。CLI の判定成功だけで警報配送済みにしない。
5. 実環境の故障試験は、独立 Worker / D1 / Queue と合成データだけを使う構成を先にレビューする。既存の APNs 鍵・実トークンをコピーしない。429→成功、5xx→再試行→打ち切り、待機中の停止・取り消し・更新を実時間で確認する。APNs の公式 endpoint を故意に過負荷にしない。追加リソースと配置の承認を得るまでは作成しない。
6. 負荷試験もこの分離構成で行い、対象件数・同時数・時間・CPU / D1 / Queue の停止予算を先に固定する。受け付け数、成功・失敗数、DB更新数を数え、別 isolate の JWT を含めて測る。予算超過・実配信・秘密の露出があれば中止する。

## 判定

コード側の監視と検証を先に PR で届ける。実環境の集計権限、metadata の秘匿、定期監視と受信先への到達、分離した障害・負荷試験は別ゲートである。これらが残る間は QA-001 を close しない。X 接続は LEGAL-001 / X-001、一般公開は AUTH-003 / RELEASE-001 の判断を待つ。
